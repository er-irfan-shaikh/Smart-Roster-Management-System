1. Relational Database Schema (SQL DDL)

In interviews, explain that the app's in-memory state (`DB`) mirrors these exact 6 normalized SQL tables in PostgreSQL/MySQL: 

-- 1. Operational Pods & Pod Leads
CREATE TABLE pods (
    pod_id VARCHAR(20) PRIMARY KEY,
    pod_name VARCHAR(100) NOT NULL,
    pod_lead_name VARCHAR(100) NOT NULL
);

-- 2. D2C Client Brands (80% Single-Resource, 20% Multi-Resource)
CREATE TABLE brands (
    brand_id VARCHAR(20) PRIMARY KEY,
    brand_name VARCHAR(100) NOT NULL,
    pod_id VARCHAR(20) REFERENCES pods(pod_id),
    staffing_model VARCHAR(15) CHECK (staffing_model IN ('SINGLE', 'MULTI')),
    operating_calendar VARCHAR(30) NOT NULL
    -- '365_DAYS' | 'NO_PUBLIC_HOLIDAYS' | 'MON_SAT_NO_HOLIDAYS'
);

-- 3. Brand Process Rules (Granular process calendars & minStaff)
CREATE TABLE brand_process_rules (
    brand_id VARCHAR(20) REFERENCES brands(brand_id),
    process_code VARCHAR(10) CHECK (process_code IN ('CS','ACC','NDR','RET')),
    operating_calendar VARCHAR(30) NOT NULL,
    min_staff_weekday INT DEFAULT 1,
    min_staff_sunday INT DEFAULT 1,
    PRIMARY KEY (brand_id, process_code)
);

-- 4. Employees (Dedicated Owners, Specialists & Pod Floaters)
CREATE TABLE employees (
    emp_id VARCHAR(20) PRIMARY KEY,
    full_name VARCHAR(100) NOT NULL,
    role_type VARCHAR(30) NOT NULL,
    pod_id VARCHAR(20) REFERENCES pods(pod_id),
    preferred_week_off INT CHECK (preferred_week_off BETWEEN 0 AND 6)
);

-- 5. Many-to-Many Employee <-> Brand Process Assignments
CREATE TABLE employee_assignments (
    emp_id VARCHAR(20) REFERENCES employees(emp_id),
    brand_id VARCHAR(20) REFERENCES brands(brand_id),
    process_code VARCHAR(10),
    is_primary BOOLEAN DEFAULT TRUE,
    PRIMARY KEY (emp_id, brand_id, process_code)
);

-- 6. Monthly Roster Schedule Fact Table (Power BI / Excel Ready)
CREATE TABLE monthly_roster (
    roster_date DATE NOT NULL,
    emp_id VARCHAR(20) REFERENCES employees(emp_id),
    status VARCHAR(20) NOT NULL,
    -- 'WORK' | 'BACKUP' | 'WEEK_OFF' | 'HOLIDAY' | 'LEAVE' | 'COMP_OFF'
    covered_brand_id VARCHAR(20) NULL,
    covered_processes VARCHAR(50) NULL,
    PRIMARY KEY (roster_date, emp_id)
);

2. Deterministic Roster Solver Logic (Python / JS)

How our two-pass heuristic scheduling engine generates rosters and resolves coverage gaps: 

def generate_monthly_roster(month_days, brands, employees, holidays):
    # PASS 1: Assign Primary Schedules (Respecting Hard Leaves & Calendars)
    for day in month_days:
        for emp in employees:
            if day in emp.planned_leaves:
                roster[emp.id][day] = "LEAVE"
            elif day in emp.comp_offs:
                roster[emp.id][day] = "COMP_OFF"
            elif not emp.any_assigned_brand_operates_on(day, holidays):
                # Brand is closed on Sunday or Public Holiday
                roster[emp.id][day] = "HOLIDAY" if day in holidays else "WEEK_OFF"
            elif day.weekday == emp.preferred_week_off:
                roster[emp.id][day] = "WEEK_OFF"
            else:
                roster[emp.id][day] = "WORK"

    # PASS 2: Validate Brand-Process Coverage & Assign Pod Backups
    for day in month_days:
        for brand in brands:
            for proc in brand.active_processes(day, holidays):
                active_staff = count_working_staff(brand, proc, day)
                if active_staff < proc.min_staff(day):
                    # Try 1: Override soft preferred week-off on multi-resource brand
                    # Try 2: Assign available Pod Float / Pod Lead from same Pod
                    backup_emp = find_available_pod_floater(brand.pod_id, proc, day)
                    if backup_emp:
                        roster[backup_emp.id][day] = f"BACKUP:{brand.id}"
                    else:
                        flag_hard_conflict(brand, proc, day, active_staff)

3. Answers to Section 8 ("Tell Us How You Think")

Q1. How did you model employees, brands, processes, pods, and their relationships?

I used a relational data model with 4 core entities: Pods (1-to-many with Brands and Employees), Brands (each having process-level rules for CS, ACC, NDR, RET), Employees (categorized into Dedicated Owners, Process Specialists, and Pod Floaters/Leads), and a junction relationship Employee-Brand-Process Assignments so an employee can own all processes for 1 brand or specific processes across multiple brands.

Q2. How does your system generate a roster and determine whether it satisfies constraints?

It uses a deterministic Two-Pass Constraint Solver. Pass 1 assigns individual employee states based on hard non-availability (Planned Leaves, Comp-Offs), brand operating calendars (365-day, No-Holidays, Mon-Sat), and preferred weekly offs. Pass 2 evaluates daily coverage per `(brand, process, day)` against `minStaff` and either assigns cross-trained Pod Float backups or flags hard conflicts vs. soft preference warnings.

Q3. How did you handle single-resource brands (80%) vs. multi-employee brands (20%)?

For Single-Resource Brands (16 brands), 1 employee handles CS+ACC+NDR; when that owner takes a weekly off or leave on an operating day (e.g., a 365-day brand), the engine routes coverage to the Pod's Float Specialist or Pod Lead. For Multi-Resource Brands (4 brands), coverage is validated per process (e.g. CS requires 2 staff on weekdays, 1 on Sunday; NDR runs Mon-Sat), staggering weekly offs among the assigned specialists first before pulling a Pod Floater.

Q4. What happens when an employee managing all processes for a brand is unavailable on a required day?

The system immediately detects that all active processes for that brand have dropped to `0/1` coverage on a required operating day. It raises a Critical Coverage Gap alert and provides a 1-click recommendation showing available cross-trained Pod Floaters/Leads in the same Pod who can step in as `BACKUP` for that specific date without regenerating the entire monthly roster.

Q5. How does your system handle conflicting requirements or insufficient staffing?

Instead of silently producing an invalid schedule, the system separates Mandatory Constraints (Client Coverage SLAs, Approved Leaves) from Soft Preferences (Preferred Weekly Off day). Mandatory client coverage takes priority over a preferred weekly off (generating an amber Soft Warning), and if total pod capacity is exceeded, it highlights the exact `(Brand, Process, Day)` in red as an unresolved Hard Conflict for manager intervention.

Q6. Which parts did you automate, and which did you leave under human control? Why?

I automated initial 30-day roster generation, operating calendar compliance, real-time gap detection, and backup candidate filtering. However, mid-month leave overrides, client rule upgrades, and final conflict approvals remain under human control (with 1-click assistance) because operations managers have real-world context on client escalations and employee burnout.

Q7. If the company doubled its team and brand count (60+ staff, 40+ brands), what would you change?

I would migrate the `localStorage` state to a PostgreSQL backend with REST APIs, replace the greedy two-pass solver with Google OR-Tools (CP-SAT Integer Linear Programming in Python) to globally optimize fairness across pods, and add role-based authentication so each Pod Lead approves their own pod's roster.

Q8. If you had one additional week, what would you improve first?

I would add historical ticket/order volume forecasting per brand (integrating Shopify/Helpdesk metrics) so `minStaff` dynamically scales on high-volume sale days, along with automated Slack/WhatsApp shift-change notifications for employees.
